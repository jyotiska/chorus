# Custom problem statements in Chorus

Add **Other** as the fifth option in the Chorus experiment brief picker. A user can type or paste a multiline brief, choose the agents and models, and start the same Plan → Build → Judge flow. The selected agents plan the work in `SPEC.md`, produce the deliverables in Git, and receive an evidence-based final review.

## Setup and saved runs

- Selecting **Other** closes the picker and focuses a multiline **Problem statement** field. The user can describe the work in their own words and mention desired formats or files in the same field. Keep the draft when they switch between **Other** and a preset during setup, and preserve their team, agent model, and judge model selections.
- Submit through `POST /api/v2/experiments` with `problemId: "other"` and `customStatement`, alongside the existing participant and model fields. Require a nonblank statement for `other`, reject a custom statement paired with a preset, and leave existing preset requests valid. Set a generous text limit after checking prompt fit for both selected models. Show the limit and any validation errors in setup so users can edit and retry. Never silently truncate the brief.
- Snapshot the original text with its line breaks as `problem.statement` at creation. Use a short first-line label for the run title, with **Custom problem** as a fallback. Keep the full brief available in the run and archive. Resume from that snapshot even if the setup draft or catalog changes. Keep the statement in the experiment snapshot and out of the shared benchmark request config.
- Scope **Other** to the experiment launcher and catalog. Pass experiment mode explicitly in the web launcher before changing the catalog version. The current web entry point and launcher use an exact `experiments-1` version check to identify experiment mode. [Launcher](../web/components/harness/setup.tsx) · [Web entry point](../web/components/harness/app.tsx) · [Experiment contracts](../chorus/harness/models.py) · [Experiment catalog](../chorus/harness/experiment_catalog.py)

## Plan → Build → Judge

### Plan · Agree on what to deliver

Each selected agent contributes to the shared specification and task distribution. Keep their existing personas and model selections. For **Other**, give agents task-neutral instructions so a QA engineer can review itinerary constraints or script continuity and a designer can work on presentation without assuming there is an app to build. Pass the original brief as user task content, below harness-owned instructions and tool permissions.

The planners agree on a small structured deliverable plan. Record the expected files or repository changes, primary output, required versus optional items, acceptance criteria, and assumptions. For each output record whether its format came from the brief or was inferred. Honor explicit formats when supported. Otherwise select the simplest usable format for the request. Record material assumptions and proceed when a reasonable draft is possible. For example, if travel dates are absent, produce a flexible itinerary with assumptions visible in the output.

Add a Plan-only tool to publish the structured plan through the existing SPEC lease and revision checks. Store the typed plan as experiment state and render its summary in `SPEC.md` from the same write. On the last `plan_complete`, validate and lock the agreed plan in the same state transition that starts Build. An invalid or stale plan should return a fixable error while the last planner can still act. Preserve all selected agents’ planning completions and the existing task checklist workflow. Avoid a separate model call to classify the request. [Phase transitions and worker prompts](../chorus/harness/experiment.py) · [SPEC state and leases](../chorus/harness/experiment_spec.py)

### Build · Put the outputs in the experiment repo

Reuse the starter, isolated repository, per-agent worktrees, local commits, PR reviews, and merges into `main`. Give custom runs a writable `deliverables/` directory for documents and assets, alongside the existing `frontend/` and `backend/` paths for briefs that ask for software. Keep `SPEC.md` managed by its existing tools. Text and static HTML fit the current UTF-8 write primitive once it accepts the new directory. Validate canonical paths, reject traversal and symlinks, and apply existing size, actor, phase, and cancellation checks. [Git workspace](../chorus/harness/experiment_git.py) · [Workspace tools](../chorus/harness/experiment_tools.py)

Keep formats capability-aware. The first release should support Markdown, plain text, static HTML, other UTF-8 formats the tools can write, and software changes using the existing starter. For an explicit binary or external-data requirement the runtime cannot satisfy, record the requirement, explain the gap, and deliver any useful supported portion. Show that gap in Results. For an inferred format, choose from the capabilities available to the selected run. Add image generation as a follow-on using a configured asset tool with validated binary writeback into the assigned worktree. The chosen agent model still coordinates the work. The image tool produces the asset and records its cost and provenance. A brief that requires current prices or availability needs a research tool or user-provided sources. Otherwise label such details as unverified.

At the end of Build, freeze the accepted deliverable plan, final `main` commit, final SPEC revision, and evidence cursor together. Build an artifact index from committed files at that SHA. Check required path presence, file type, nonempty content, and any supported format validation. Record missing or invalid items explicitly and continue to Judge so incomplete work still receives a review. For code deliverables, link to the frozen repository and relevant changes. Work left on an agent branch remains inspectable as contribution evidence. [Freeze and judge retry](../chorus/harness/experiment.py) · [Repository browsing routes](../chorus/harness/routes.py)

### Judge · Review the deliverable and each agent

- For **Other**, replace the app quality rubric with five stable criteria for **Deliverable quality**. Assess brief coverage, correctness or internal consistency, completeness, clarity and usability, and format or presentation quality. Use the brief and acceptance criteria to interpret each dimension. The judge checks continuity and pacing for a sitcom, for example, and day-to-day sequencing and travel constraints for an itinerary.
- Keep the existing individual and collaboration criteria and 0–4 scoring. Require citations from frozen records for claims about agent work, with artifact paths for findings about the output. Credit substantive planning, review, or verification even when an agent authored no merged file. Separate file checks the harness performed from model judgments and use the existing `not_assessable` and `not_applicable` values where warranted. For custom software tasks, apply the same evidence limit on runnability as preset apps.
- Keep the current report shape where possible. Persist a rubric identifier and use it to select the prompt, validation rules, and Results labels so older reports retain their original interpretation. Retry Judge against the same commit, plan, artifact index, rubric, and evidence. Keep the built-in app rubric for the four preset briefs. [Judge prompt and validation](../chorus/harness/experiment.py) · [Results and scorecards](../sdk/harness-workspace.tsx)
- In Results, list the primary artifact first, followed by supporting files and missing required outputs. Provide **Open** and **Download** for committed files at the frozen SHA. Reuse the repository text viewer and serve downloads as attachments. Show generated HTML as source in the viewer so its scripts never execute in the Chorus page. Keep results, downloads, and score evidence linked to the same commit on reload. [Live workspace](../web/components/harness/live.tsx) · [Repository viewer](../sdk/harness-workspace.tsx)

## Example runs

| User brief | Agreed output | Review focus |
|---|---|---|
| Plan a three-day trip to Bangkok for a family that wants minimal walking. | `deliverables/itinerary.md` with daily options, transport, rest breaks, and assumptions | Three complete days, realistic sequencing, and fit for the group |
| Write an original workplace sitcom pilot. | `deliverables/pilot.md`, with character notes as a supporting file if the plan calls for them | Format, comic pacing, character consistency, and whether the pilot tells a complete story |
| Make the pilot a single HTML file. | `deliverables/pilot.html` as the primary download | Requested format, complete script, and readable presentation |
| Build a small habit tracker. | Frozen repository with frontend or backend changes and a link to the main code | Brief coverage, completeness, and what can be verified by inspection |
