# Docker, Browser, Terminal, and repository previews in Chorus

Launch the full Chorus app with Docker Compose. In a repository experiment, the tab order becomes **Board → Canvas → Repository → Results → Browser → Terminal**. **Run** starts the generated frontend and backend and opens the frontend in Browser. Terminal opens an interactive shell in the same isolated workspace. Repository displays highlighted, wrapped source and opens Markdown in **Preview** by default.

This plan records the design and verification targets for local, single-user Chorus. The default preview source is the latest committed `main` until frozen evidence exists, then the commit used for Results. A running workspace keeps its source revision until the user chooses to load a newer one. [Current setup and usage](running-chorus.md)

## 1. Run the complete Chorus app in Docker

- Add a root `Dockerfile`, `.dockerignore`, and `compose.yaml`. Use a multi-stage build with the locked Python dependencies, Node 24, the production Next.js build, and Git. Start the web interface and one Python engine inside the app container. Adapt the existing supervisor for container networking, readiness, signal forwarding, and graceful shutdown. Keep the engine on the container's loopback interface and publish the web interface to host loopback. `docker compose up --build` is the normal startup path and requires only Docker and Compose on the host. [Chorus launcher](../chorus/cli/launcher.py) · [Docker Compose service configuration](https://docs.docker.com/reference/compose-file/services/)
- Put SQLite and experiment repositories under one durable data volume at stable container paths. Document explicit backup and import from existing source installations. Check stored absolute workspace paths and Git worktree references during import, and test opening and resuming a copied run before documenting it as supported. Keep provider keys in the engine's runtime configuration. Exclude local `.env` files, generated workspaces, and databases from the image build context. Document how containerized Chorus reaches host Ollama on macOS and Linux. [Existing configuration and recovery](running-chorus.md)
- Add a separate runner image and a small private Docker controller. The controller alone gets access to the local Docker daemon and accepts only fixed operations on Chorus-owned resources. The engine communicates with it through a private control channel and resolves the experiment, revision, launch profile, and permissions. The web layer transports UI requests and streams. [Docker daemon trust boundary](https://docs.docker.com/engine/security/#docker-daemon-attack-surface)

**Acceptance.** Compose starts the interface, engine, and experiment flow with a fake provider on a host without Python or Node tooling. Recreating the app container preserves its database, repositories, and recorded results. A second engine cannot open the same store. Check custom host ports, a port collision, health failures, Ctrl-C and termination, configuration with a local provider, and a representative import with existing worktrees. Smoke-test Linux and Docker Desktop on Apple Silicon.

## 2. Start the generated repository with Run

The Browser tab shows the source commit and a **Run** button. The engine resolves the source commit with the same Git ancestry checks used by Repository. It copies committed files into a writable workspace in a per-experiment runner container. Terminal and Run share that copy, so Terminal changes are available to the preview. Label the source commit and explain that workspace edits are temporary. A newer merge changes the available source, and loading it replaces the temporary copy through an explicit reset. [Repository routes](../chorus/harness/routes.py) · [Experiment Git handling](../chorus/harness/experiment_git.py)

1. Inspect the projects under `backend/` and `frontend/`. Support the bundled Node starter first, including saved copies. Support compatible npm projects with an explicit launch profile and use a lockfile when present. Start the backend, verify readiness, and start the frontend with the backend URL set inside the workspace. Run installation and every project command inside the runner. Give unsupported layouts and missing scripts actionable Terminal instructions.
2. When the frontend returns a ready response, open its URL in Browser automatically. Route preview traffic through a loopback-only gateway that maps a registered workspace and port to the runner. Verify the routing with the existing starters, which bind to `127.0.0.1` inside the runner. Use a connection relay that reaches the runner's loopback interface so saved repositories work with their original binding. Preserve HTTP requests, streaming responses, WebSocket upgrades, and allowed redirects for normal app behavior and hot reload. Terminal users can explicitly forward a server port through the same gateway. [Frontend starter](../chorus/harness/starters/frontend/server.mjs) · [Backend starter](../chorus/harness/starters/backend/server.mjs) · [Docker port publishing](https://docs.docker.com/engine/network/port-publishing/)
3. Show **Starting**, **Running**, **Stopped**, or **Failed** with per-service logs and an actionable failure message. Coalesce repeated Run requests. If startup fails partway, stop the services from that attempt and free its routes. Report a conflict with a manually started server and let the user decide how to use its port. **Stop** ends the managed frontend and backend while keeping the open shell and its workspace available. Reclaim preview routes, containers, and scratch data on runtime reset and application shutdown, and recover or reclaim labeled resources after a crash.

Run generated code as a non-root user with bounded CPU, memory, processes, output, and disk use. Give the runner access to its scratch workspace and dependency registries through controlled egress. Keep the host filesystem, Docker daemon, provider credentials, Chorus control services, and other experiment workspaces outside its reach. Keep preview actions and logs separate from the experiment's Git history, judge evidence, and model usage ledger.

**Acceptance.** Start a fixture with **Run**, verify that the backend is reached through the frontend, and complete an interaction that persists through the backend. Repeat on a saved starter that binds to loopback. Cover a lockfile install through a test registry, custom commands, a missing script, readiness timeout, port conflict, duplicate Run clicks, stop and retry, partial-start cleanup, application restart, and two simultaneous experiments. Verify that a merge during a run leaves the displayed source pinned and that temporary edits leave the saved commit and Results intact.

## 3. Add the Browser tab

Use a sandboxed iframe with an address bar, **Back**, **Forward**, and **Refresh**. It runs the generated app in the user's browser, including its JavaScript and forms. The address bar accepts paths and URLs for the current workspace's forwarded services. An **Open in new tab** action lets the user continue outside the iframe where embedding restrictions apply. [iframe behavior and restrictions](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)

Give each forwarded service a dedicated loopback origin, separate from Chorus. Serve a small wrapper on that origin around the app frame. It observes the child frame's same-origin navigation, including redirects and client-side routes, and relays the URL and history state to the Chorus toolbar. The toolbar sends navigation commands to that wrapper, so Back and Forward use the preview history. Keep messages limited to navigation, with validated payloads, exact origins, and the expected frame window. Preserve the app's embedding policies and show a useful fallback when the frame or history bridge is unavailable. Keep the frame mounted when switching workspace tabs. [Navigation API](https://developer.mozilla.org/en-US/docs/Web/API/Navigation) · [Cross-origin messaging](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage) · [Frame embedding policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors)

**Acceptance.** In Chromium and WebKit, test address entry, links, redirects, forms, client-side routes, query strings and fragments, toolbar button states, Back and Forward across both full loads and client-side routes, and Refresh on the current page. Verify hot reload or a fixture WebSocket, tab switching, keyboard focus, a stopped preview, and the embedding fallback. Verify the preview cannot navigate the Chorus window or access its control endpoints, and that rejected postMessages and unregistered ports cannot change the workspace or reach an upstream service.

## 4. Add the Terminal tab

Use xterm.js connected over a WebSocket to a real PTY in the runner. The shell starts at the root of the workspace and includes the tools in the pinned runner image, including Bash, Git, Node/npm, and Python. Send raw terminal input and output and forward resize events. Keep one shell per workspace across tab switches and briefly across network interruptions. Bound buffered output, identify the session and active connection, and handle disconnect, shell exit, and restart explicitly. Keep terminal I/O out of ordinary engine logs and model context. [xterm.js documentation](https://xtermjs.org/docs/)

**Acceptance.** Test pipelines, Unicode, ANSI colors, shell history, paste, interactive input, resize, Ctrl-C, and an interactive program. From Terminal, start a fixture server, forward its port, and open it in Browser. Verify Run uses changes in the same workspace. Cover reconnection, shell exit, stale connections, output pressure, and cleanup. Verify that an unrelated browser origin cannot attach or send input, and that the runner cannot access host files, secrets, the control plane, or another experiment's workspace.

## 5. Improve Repository file viewing

- Replace the plain text block with a lightweight, read-only code viewer. Load syntax grammars on demand for common Chorus files, map names and extensions to known languages, and fall back to plain text. Enable word wrap by default and preserve native text selection and copying. Keep the binary, empty, and oversized file states, including the current 128 KB API limit. Keep file requests pinned to their branch and revision. [Shared repository viewer](../sdk/harness-workspace.tsx)
- For `.md` and `.markdown`, offer **Preview** and **Raw**, with Preview selected when a Markdown file opens. Reuse the existing `react-markdown` and GFM pipeline with raw HTML disabled. Raw shows the original source through the wrapped viewer. Open repository-relative file links in the selected commit's file viewer. Serve supported raster images through a bounded endpoint using committed Git objects with verified media types. Apply the shared viewer to the same file surfaces in Results so frozen copies render consistently. [GFM support](https://github.com/remarkjs/remark-gfm) · [React Markdown security](https://github.com/remarkjs/react-markdown#security)
- Edit shared repository UI in `sdk/` and regenerate the integrated Chorus copies. Keep Browser and Terminal UI in `web/`, and use the Python contracts and stable error codes for new runtime endpoints. Add the tabs to repository experiments only. Saved benchmarks and historical archives continue through their existing entry points.

**Acceptance.** Test representative JS/TS, Python, JSON, CSS, and unknown extensions. Assert syntax tokens render, long lines wrap at narrow widths, and text can be selected without editing. Exercise empty, binary, oversized, loading and failed files, and rapid branch and file changes. For Markdown, test default Preview, exact Raw text, switching files, headings, lists, tables, fenced code, links and relative assets, and safe treatment of raw HTML and unsafe URLs. Verify the frozen Results file view, branch diffs, benchmark views, and archived sessions.
